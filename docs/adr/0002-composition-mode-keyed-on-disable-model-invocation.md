# Composition mode keyed on `disable-model-invocation`, scoped to Claude Code only

The four pipeline skills (to-vision, to-pitch, to-roadmap, to-milestone) need a policy for composing with grilling, domain-modeling, research, prototype, wayfinder, to-spec, to-tickets, and implement. Rather than deciding invoke-vs-defer-vs-embed per referenced skill from scratch, we key it off a signal the tooling already enforces: the `Skill` tool refuses to invoke any skill flagged `disable-model-invocation` and explicitly forbids replicating its workflow by other means. Unflagged skills (grilling, domain-modeling, research, prototype) are **invoked** directly. Flagged skills (wayfinder, to-spec, to-tickets, implement) are **deferred** to the human. **Embed** stays a narrow third option for folding a single short discipline inline, not a general alternative to invoke.

Because the `Skill` tool itself is Claude-Code-only (per Portability boundary & target runtimes, #10), we scope the four new skills to Claude Code via `compatibility` frontmatter rather than building a graceful-degrade path for non-Claude-Code hosts. This forecloses a fourth **adapt** mode (restating a skill's protocol inline as a portability fallback) — there's no portable case left for it to serve.

Considered options: a graceful-degrade "adapt" mode for invoke-mode skills on hosts without the `Skill` tool (rejected — the whole pipeline already depends on Claude-Code-only mechanics elsewhere, e.g. wayfinder's own `disable-model-invocation` gate and research's subagent dispatch, so a partial degrade for just this one composition axis buys little portability in practice).
