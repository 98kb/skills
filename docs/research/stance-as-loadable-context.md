# What form does a stance take when its job is to be loaded as context?

Research for [#84](https://github.com/98kb/skills/issues/84), Q7 of [#80](https://github.com/98kb/skills/issues/80), under [Map #81](https://github.com/98kb/skills/issues/81). The artifact is a durable record of a founder's stance, loaded as **context enrichment** for a human or agent working downstream on the product-planning pipeline — never impersonation, never an authority. Length and structure are constraints, not preferences: the artifact competes for context budget with the vision/pitch/roadmap artifacts it accompanies, and a stance nobody can afford to load is a stance nobody reads.

Source base is deliberately disjoint from the sibling tickets: agent-memory systems, context engineering, retrieval design, and first-party documentation from model providers and agent frameworks on how persistent context is structured, budgeted, and injected. Nothing from oral-history method or clinical charting appears here — [#83](https://github.com/98kb/skills/issues/83) owns that. Every number below comes from a first-party doc, a published paper, or a lab's own technical report; where a claim is an inference from a measurement rather than the measurement itself, it says so.

## Q1 — One document, or a short core plus retrievable detail?

**Verdict: short core plus retrievable detail, unanimously. Every shipped persistent-context system found — across two model providers and one agent framework — is a two-tier design, and each tier carries a published size cap on the always-loaded part and none at all on the retrievable part.**

- Anthropic's Skills design is explicitly three-level: frontmatter `name` + `description` are pre-loaded for every installed skill and give "just enough information for Claude to know when each skill should be used without loading all of it into context"; the SKILL.md body loads only "if Claude thinks the skill is relevant"; bundled files are "the third level (and beyond) of detail, which Claude can choose to navigate and discover only as needed" ([Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)).
- The economics of that split are stated outright: "No context penalty for large files. Reference files, data, or documentation don't consume context tokens until actually read" — and correspondingly, "Bundle comprehensive resources: include complete API docs, extensive examples, large datasets; no context penalty until accessed" ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). The cost is entirely in tier one, so tier one is what needs a budget.
- Claude Code's auto memory is the same shape with harder numbers: "`MEMORY.md` acts as an index of the memory directory," of which only "the first 200 lines … or the first 25KB, whichever comes first, are loaded at the start of every conversation," while "topic files like `debugging.md` or `patterns.md` are not loaded at startup. Claude reads them on demand" ([Claude Code memory](https://code.claude.com/docs/en/memory)). The runtime actively enforces it: exceed the limit and "Claude Code returns an error telling Claude to rewrite the index, because everything past the limit is dropped on the next load."
- MemGPT's whole thesis is this split, borrowed from OS virtual memory: a fixed-size **main context** holding system instructions plus a "fixed-size read/write block of unstructured text" of "key facts, preferences, and other important information," against an **external context** of arbitrary-length archival storage that "must always be explicitly moved into main context" to be used ([MemGPT](https://arxiv.org/abs/2310.08560)). Letta ships it with an explicit numeric cap: memory blocks "are always visible - no retrieval needed" and carry a `limit` field setting "the size limit (in characters) of the block" ([Letta — Memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks)).
- The one system with no second tier publishes the sharpest warning about it. CLAUDE.md files are "loaded in full regardless of length" — and the guidance is "**Size**: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence," with the explicit note that "splitting into `@path` imports helps organization but doesn't reduce context, since imported files load at launch" ([Claude Code memory](https://code.claude.com/docs/en/memory)). Splitting a stance across files buys nothing unless the split is also a *loading* boundary.

**Net:** a single stance document is the one shape no source endorses. The choice is between a small always-loaded core with retrievable detail behind it, and a core with nothing behind it — and the second only works if the entire stance fits the core budget.

## Q2 — Loaded wholesale, or the relevant position retrieved per question?

**Verdict: retrieved per question for the positions, wholesale for a deliberately small index — and the strongest single measurement in the whole source base is a direct wholesale-vs-focused comparison that wholesale loses.**

- Chroma's LongMemEval run is the closest available analogue to this artifact's actual use: a question answered against a **focused prompt of ~300 tokens** containing only the relevant material, versus a **full prompt of ~113k tokens** containing the same material embedded in the complete history. "Across all models, we see significantly higher performance on focused prompts compared to full prompts" ([Context Rot](https://www.trychroma.com/research/context-rot)). Same information, same model, same question — the only variable is whether it arrived wholesale or retrieved.
- Anthropic's own recommendation is just-in-time by default: "Rather than pre-processing all relevant data up front, agents built with the 'just in time' approach maintain lightweight identifiers and use these references to dynamically load data into context at runtime using tools." It also names the cost honestly — "there's a trade-off: runtime exploration is slower than retrieving pre-computed data" — and lands on a middle position: "the most effective agents might employ a hybrid strategy, retrieving some data up front for speed, and pursuing further autonomous exploration at its discretion" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).
- Anthropic's memory tool is built on the same premise: "Memory supports just-in-time context retrieval. Rather than loading all relevant information up front, an agent records what it learns in memory files and reads them back on demand. This keeps the active context focused on the current task" ([Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). Note the retrieval protocol is a directory listing followed by targeted `view` calls — filesystem navigation, not vector search.
- **The dissent, and it is a real one.** Google's first-party long-context guidance argues the opposite: a "paradigm shift" toward "providing all relevant information upfront" rather than RAG, on the strength of "~99%" single-needle retrieval accuracy. But the same page limits its own claim: performance "can vary to a wide degree depending on the context" when multiple needles are needed, and achieving 99% accuracy on 100 pieces of information "requires approximately 100 separate requests," which offsets the savings ([Gemini — Long context](https://ai.google.dev/gemini-api/docs/long-context)). OpenAI records the same boundary: "long context performance can degrade as more items are required to be retrieved, or perform complex reasoning that requires knowledge of the state of the entire context" ([GPT-4.1 Prompting Guide](https://developers.openai.com/cookbook/examples/gpt4-1_prompting_guide)). A downstream dilemma needs *one* position, not a hundred — which is the single-needle regime where the wholesale case is strongest, and also the regime where retrieval is cheapest.
- Worth stating plainly: no source found measures whether wholesale loading of a ~2k-token document harms anything. The measured wholesale penalties are all at 32k–113k tokens. A stance that genuinely fits in 200 lines is below the range where any of this evidence bites.

## Q3 — What structure makes one position findable by an agent arriving with a specific dilemma?

**Verdict: an entry-point index whose lines state *when to consult this*, not *what this is about*; discrete, separately addressable positions rather than narrative; and — the load-bearing finding — the index must carry the vocabulary of the incoming dilemma, because retrieval collapses precisely when question and target don't share wording.**

- **The failure mode is lexical, and it is large.** NoLiMa holds the retrieval task constant and removes only the lexical overlap between question and target: "at 32K, for instance, 11 models drop below 50% of their strong short-length baselines," and the best performer fell "from an almost-perfect baseline of 99.3% to 69.7%" ([NoLiMa](https://arxiv.org/abs/2502.05167)). Chroma reproduces the effect continuously, varying needle-question cosine similarity across 0.445–0.829 and finding "performance degrades more quickly in input length with lower similarity needle-question pairs" ([Context Rot](https://www.trychroma.com/research/context-rot)). An agent arriving with "should we add a second button for power users?" will not lexically match a stance section headed "Interface philosophy." This is the exact condition both papers measure, and it is the main design constraint on the index.
- Anthropic's answer to the same problem in Skills is a discovery string carrying trigger vocabulary: the `description` is capped at **1,024 characters**, is "critical for skill selection: Claude uses it to choose the right Skill from potentially 100+ available Skills," and must "include both what the Skill does and when to use it," with the worked pattern being an explicit trigger clause — "Use when working with PDF files or when the user mentions PDFs, forms, or document extraction" ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). Transposed: each stance entry needs a *when this applies* clause written in the dilemma's language, not a topic label.
- Structural rules from the same doc, all directly transferable: "Keep references one level deep from SKILL.md" — because with nested references "Claude might use commands like `head -100` to preview content rather than reading entire files, resulting in incomplete information"; "For reference files longer than 100 lines, include a table of contents at the top … so Claude can see the full scope of available information even when previewing with partial reads"; and organise by domain "to avoid loading irrelevant context," with `grep` given as the intended lookup mechanism over the reference directory.
- Claude Code ships a conditional-loading mechanism that is a near-exact fit for "load this position only when the work touches its subject": rules with `paths:` frontmatter "only load into context when Claude works with matching files, reducing noise and saving context space" ([Claude Code memory](https://code.claude.com/docs/en/memory)). Same doc, on the choice between tiers: "For task-specific instructions that don't need to be in context all the time, use skills instead, which only load when you invoke them or when Claude determines they're relevant."
- **Where the canonical retrieval function does not transfer.** Generative Agents scores memories as `α_recency·recency + α_importance·importance + α_relevance·relevance`, with all three α set to 1, recency an exponential decay of factor 0.995 per sandbox hour, importance a 1–10 poignancy rating, relevance an embedding cosine similarity, all min-max normalised ([Generative Agents](https://arxiv.org/abs/2304.03442)). For a *point-in-time* record, recency is meaningless — every entry is equally old by construction — and importance is set by the subject at authoring time, not accrued. Only the relevance term survives, which is why Q3 reduces to the lexical-matching problem above rather than to a ranking problem.
- One suggestive result to hold loosely: Chroma found that "models perform worse when the haystack preserves a logical flow of ideas. Shuffling the haystack and removing local coherence consistently improves performance." That is a finding about *surrounding distractor text*, not about how the target itself is written, so reading it as "write the stance as discrete entries rather than as narrative" is an inference, not a measurement. It happens to point the same way as everything else here.

## Q4 — What do the measurements actually say about long documents degrading attention to the rest of the window?

**Verdict: the folklore overstates what has been measured. There is a large, replicated literature on models failing to *retrieve from* long contexts, and essentially no primary measurement of the specific claim that a long document degrades attention to everything else in the window. "Context rot" is a lab coinage, not a peer-reviewed finding; the peer-reviewed finding is positional.**

- **What is measured, and by whom.** Liu et al. establish the positional result: "performance is often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle of long contexts, even for explicitly long-context models" ([Lost in the Middle](https://arxiv.org/abs/2307.03172), TACL). RULER establishes the length result across 17 models: "while these models all claim context sizes of 32K tokens or greater, only half of them can maintain satisfactory performance at the length of 32K" ([RULER](https://arxiv.org/abs/2404.06654)). NoLiMa establishes the lexical result (above). Chroma establishes non-uniformity across 18 models: "models do not use their context uniformly; instead, their performance grows increasingly unreliable as input length grows" ([Context Rot](https://www.trychroma.com/research/context-rot)).
- **Where the term comes from.** Anthropic uses "context rot" and attributes it to exactly this study: "studies on needle-in-a-haystack style benchmarking have uncovered the concept of context rot: as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). That is a claim about recall *from* the long context — not about collateral damage to other material.
- **The mechanism offered for collateral damage is a model, not a measurement.** Anthropic's argument is architectural: "LLMs are based on the transformer architecture, which enables every token to attend to every other token across the entire context. This results in n² pairwise relationships for n tokens … as its context length increases, a model's ability to capture these pairwise relationships gets stretched thin." Hence "context, therefore, must be treated as a finite resource with diminishing marginal returns," and "LLMs have an 'attention budget' … every new token introduced depletes this budget by some amount." Persuasive and first-party, but stated as reasoning, with no accompanying experiment.
- **The closest thing to direct evidence** is Chroma's distractor work — even a single distractor reduced performance relative to a clean baseline, and distractors are non-uniform, with specific ones recurring in hallucinated answers — plus the ~300-token vs ~113k-token focused/full gap in Q2. Both show that *adding* irrelevant tokens degrades performance on a question the relevant tokens could answer. That is the failure mode in question, measured at 113k tokens, not at 2k.
- **The one first-party statement of the exact fear**, and it is an assertion with no published measurement behind it: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence," repeated as "files over 200 lines consume more context and may reduce adherence" ([Claude Code memory](https://code.claude.com/docs/en/memory)). Note "adherence," not "recall" — this is the vendor of the most widely deployed always-loaded context file saying that length costs you compliance with its own contents. It is the single most decision-relevant sentence found, and it is unevidenced.
- **Two placement findings that survive regardless of length.** Anthropic: for "large documents or data-rich inputs (20k+ tokens)," put longform data at the top, above the query, because "queries at the end can improve response quality by up to 30 percent in tests, especially with complex, multidocument inputs" ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)); Google concurs — "the model's performance will be better if you put your query / question at the end of the prompt (after all the other context)" ([Gemini — Long context](https://ai.google.dev/gemini-api/docs/long-context)). OpenAI differs on instructions specifically: "ideally place your instructions at both the beginning and end of the provided context, as we found this to perform better than only above or below," and "if you'd prefer to only have your instructions once, then above the provided context works better than below" ([GPT-4.1 Prompting Guide](https://developers.openai.com/cookbook/examples/gpt4-1_prompting_guide)). All three agree the stance belongs *before* the question, never after.

## Bottom line

**Shape.** Two tiers, not one document. A **stance index** that is always loaded, and a set of **position files** retrieved when a dilemma touches them. Every shipped persistent-context system in the source base is built this way — Skills' three levels, `MEMORY.md` plus topic files, MemGPT/Letta's main-context blocks plus archival store — and none of them ships a single flat always-loaded document. The index is not a summary of the stance; it is a *routing table*: one line per position, each line stating **when to consult it** in the vocabulary a downstream dilemma would arrive in, with a pointer to the position file. This is the Skills `description` pattern ("Use when …", ≤1,024 characters, chosen from among 100+) applied to positions instead of skills, and it is dictated by the NoLiMa/Chroma result that retrieval fails on low lexical overlap, not by taste.

**Budget, with the evidence.** Cap the always-loaded index at **200 lines / 25KB** — the two independently-set first-party limits for exactly this artifact class (CLAUDE.md "target under 200 lines … longer files consume more context and reduce adherence"; `MEMORY.md` hard-truncated at "the first 200 lines … or the first 25KB, whichever comes first"). At normal markdown prose density that is roughly **2,000–3,000 tokens** — our arithmetic, not a sourced figure. Cap each position file at **500 lines** (Anthropic's SKILL.md body limit) and add a table of contents past **100 lines** (their reference-file rule). Keep references **one level deep** from the index, because deeper nesting provokes partial `head -100` reads. Note honestly that a 200-line core sits an order of magnitude below the 32k–113k range where all the degradation measurements were taken; the budget is defensible as vendor-consistent practice and as competition for room against the pipeline artifacts, not as a measured cliff edge.

**Wholesale vs. per-question: split verdict, and it is not a fudge.** Load the index wholesale — it is small, it is cheap, and it must be present for the agent to know a position exists at all. Retrieve positions per question. The decisive evidence is Chroma's LongMemEval comparison: the same question, the same information, answered from ~300 focused tokens versus ~113k full tokens, with "significantly higher performance on focused prompts" across every model tested. Anthropic's own guidance lands in the same place ("hybrid strategy, retrieving some data up front for speed, and pursuing further autonomous exploration at its discretion"). Google is the genuine dissent — "providing all relevant information upfront" over RAG — but its own caveat (accuracy degrades on multi-needle retrieval) doesn't bite here, since a dilemma needs one position, not a hundred.

**Flagged consequence — this decides "who loads the stance, and when," which #81 currently holds as fog.** The retrieval half of the verdict removes the question's premise. Nobody "loads the stance" as a unit: the index is loaded at session start by the same mechanism that loads any always-on project context, and individual positions are pulled by the agent, mid-session, at the moment a dilemma matches an index line. Two design consequences follow immediately and should graduate into the map rather than wait for Phase 2. First, **the index is the whole discoverability surface** — a position with no index line is a position that will never be retrieved, which makes index-line wording a first-class authoring step in the interview, not formatting. Second, and directly against the map's central design risk in [#80](https://github.com/98kb/skills/issues/80): retrieval is *better* for the never-an-authority constraint than wholesale loading, because a position that enters context on a deliberate lookup is a visible, attributable act with a matching index line behind it, whereas a document sitting in the window is used silently on every question including the ones it never addressed. The boundary-marking mechanism [#83](https://github.com/98kb/skills/issues/83) is chasing therefore has a place to live: the index line, which is where "this position covers X" can be stated and where its absence is legible.

**Where the sources come up empty.** Nobody has measured the specific failure the ticket names — a long context document degrading attention to *everything else* in the window. What exists is a large replicated literature on failure to retrieve *from* long context (Liu et al.'s positional U-curve; RULER's 17 models, half failing at 32K; NoLiMa's 11 models below half their baseline at 32K; Chroma's 18-model non-uniformity), plus an architectural argument from Anthropic about n² attention and an "attention budget" that is reasoning rather than experiment, plus one unevidenced vendor assertion that longer always-loaded files "reduce adherence." "Context rot" is Chroma's coinage adopted by Anthropic, not a peer-reviewed term; the peer-reviewed name is *lost in the middle*, and it names a positional effect. The 200-line budget should be adopted because two vendors independently converged on it for this exact artifact class — not because anyone has shown a cliff there.
