# What does unranked lexical retrieval do when two routing lines match?

Research for [#118](https://github.com/98kb/skills/issues/118), blocking [#116](https://github.com/98kb/skills/issues/116) item 1, under [Map #81](https://github.com/98kb/skills/issues/81). A **stance index** is an always-loaded routing table carrying one **routing line** per position; findability is lexical rather than ranked. [ADR 0013](../adr/0013-routing-line-extent-is-fixed-revision-is-a-wording-act.md) asserted that two lines both matching is correct behaviour and a reader simply sees both, then withdrew the claim, because the only observation on record says the broader line wins. The question is which — and, above that, whether the behaviour is **specified** by anyone.

This is the first pass on this map whose subject is an agent reader rather than a human one, so the sourcing bar is narrower than usual: **first-party agent documentation only**. Nothing from human information retrieval is used, cited or transposed, and no analogy is drawn to one. The central identity is not an analogy either: a skill's frontmatter `description` and a routing line are the same mechanism — a short natural-language line, always loaded, matched by a model against an incoming task, with no ranking layer specified. Tool descriptions, MCP tool listings, subagent descriptions and `CLAUDE.md` rules are the same mechanism again, on four more surfaces.

## Q1 — Is the behaviour specified, observed, or neither?

**Verdict: not specified, on any surface, by any vendor — and the omission is structural rather than an oversight. Selection is handed to model judgement, and the vendor's own tooling treats triggering as a probability to be sampled rather than a function to be documented.**

- The canonical spec defines format and nothing else. `description` is "Max 1024 characters… Should include specific keywords that help agents identify relevant tasks" ([Specification](https://agentskills.io/specification)). No selection algorithm, no ranking, no tie-break, no statement of how many skills may match.
- The implementer's guide says why, in one sentence: "**Most implementations rely on the model's own judgment as the activation mechanism, rather than implementing harness-side trigger matching or keyword detection**" ([Adding skills support](https://agentskills.io/client-implementation/adding-skills-support)). Its five implementation steps — discover, parse, disclose, activate, manage — contain no scoring or arbitration step at all. There is no matcher for a tie-break to live in.
- Triggering is therefore a **measured** property. "**Model behavior is nondeterministic — the same query might trigger the skill on one run but not the next.**" The prescribed method is 20 labelled queries, three runs each, a **trigger rate**, and a pass threshold of 0.5 ([Optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)); Anthropic's `skill-creator` ships exactly those defaults. A behaviour whose vendor-supplied test harness reports it as a fraction is not a behaviour the docs specify.
- **The same hole sits in the same place on every comparable surface.** MCP puts selection outside the protocol — it carries `tools/list` and `tools/call`, and the step between them appears in its own diagram as a bare `Tool Selection` note; tools are "**model-controlled**." Anthropic's tool docs say "Claude determines when to call a tool based on the user's request and the tool's description," then, in the same document, "**This behavior is not guaranteed**, especially for more ambiguous prompts and for less capable models."
- **A perfect lexical match is not even sufficient.** "Agents typically only consult skills for tasks that require knowledge or capabilities beyond what they can handle alone. **A simple, one-step request like 'read this PDF' may not trigger a PDF skill even if the description matches perfectly**, because the agent can handle it with basic tools" ([Optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)). Match is not the operative predicate; *perceived need* is. This bears on the map well beyond #116 — see the flagged consequence below.
- **The one observation on record is weaker than ADR 0013 treated it as.** The prototype's line — "the two lines compete for the same words and the broader line wins by covering more of them" — appears in a revision note justifying an authoring decision taken *before publication*, on a T1 accrual its own README labels "**constructed**, not elicited." No query was run against any agent. It is an author's prediction, and it should not be cited as an observation again.

## Q2 — If both match, do both return, or does one win?

**Verdict: both. Union on load is documented, arbitrary resolution on conflict is documented, and "one wins" is documented nowhere. ADR 0013's withdrawn claim was right, and can be restored — as a reading, not a guarantee.**

- **The outright answer exists, and it is on the memory surface rather than the skills one.** For always-loaded natural-language guidance, Claude Code states it plainly: "**All discovered files are concatenated into context rather than overriding each other**," and "**if two rules contradict each other, Claude may pick one arbitrarily**" ([Memory](https://code.claude.com/docs/en/memory)). Union on load; arbitrary on conflict. That is the closest first-party statement in existence to this ticket's question, and it answers both halves of it at once.
- Skills say the same thing from the authoring side. "Once a skill activates, its full `SKILL.md` body loads into the agent's context window alongside conversation history, system context, **and other active skills**"; and "Skills scoped too narrowly **force multiple skills to load for a single task, risking overhead and conflicting instructions**" ([Best practices](https://agentskills.io/skill-creation/best-practices)). Anthropic concurs — "**Claude can load multiple skills simultaneously**… composability is one of the most powerful parts of the skills feature" ([Complete Guide to Building Skills](https://resources.anthropic.com/hubfs/The-Complete-Guide-to-Building-Skill-for-Claude.pdf), [Help Center](https://support.claude.com/en/articles/12512198-how-to-create-custom-skills)). Both loading is the documented steady state; the priced cost is *conflicting instructions*, which presupposes both arrived.
- The refusal is as informative as the finding. Across the spec, the implementer's guide, all four Anthropic skills pages and the Claude Code skills doc, **no sentence describes what happens when two descriptions both fit** — no first-match, no most-specific, no longest-overlap, no catalog-order preference. The catalog is a flat list with no stated ordering semantics. Searched and empty.
- **The tool surface is the counterweight and is reported honestly.** Parallel tool calls look like "both returned" and are not: "By default, Claude may call multiple tools in a single response," but every vendor justifies parallelism by *multiple independent operations*, never by two candidates for one operation. There, overlap appears only as a defect with an unreliability consequence — "**When tools overlap in function or have a vague purpose, agents can get confused about which ones to use**" ([Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)); "the most common failures are wrong tool selection… especially when tools have similar names" ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Note the modals: *can get confused*, *might*, *degrades*. Nobody says which wins there either.
- **Why the skills and memory evidence governs and the tool evidence does not.** A tool call is an *action*, and only one action can be right; a skill and a `CLAUDE.md` rule are *material*, and material accumulates. Two positions bearing on a dilemma are two pieces of reference material. The stance index routes to material, so the skill and memory surfaces are the near neighbours and the tool surface is the far one.

## Q3 — Is anything in the artifact's control?

**Verdict: one control is specified and the design already uses it — presence or absence in the catalog. Of the wording remedies on offer, the one ADR 0014 forecloses is narrowing; the one it does not foreclose is a negative trigger that names the neighbouring position.**

- Every deterministic rule in the mechanism resolves **name** collisions, never description overlap. "When two skills share the same `name`, apply a deterministic precedence rule… project-level skills override user-level skills… **Log a warning when a collision occurs so the user knows a skill was shadowed**" ([Adding skills support](https://agentskills.io/client-implementation/adding-skills-support)); MCP's equivalent is SHOULD-level and mandates no strategy — aggregating clients "**MAY** encounter naming collisions… and **SHOULD** implement a disambiguation strategy such as prefixing tool names with a server identifier." Both fire upstream of the model, at the identifier layer, and the loser is removed rather than ranked. Collision is handled by deletion; it is never handled by the matcher.
- The other specified control is the same shape: skills that opt out via `disable-model-invocation` must be **hidden entirely** — "Hide filtered skills entirely from the catalog rather than listing them and blocking at activation time." This is ADR 0011's residue quarantine and ADR 0012's "the absence of an index line *is* the computable no-match," arriving from the implementer's side.
- **Narrowing is offered as the overlap remedy, and it is the one ADR 0014 has closed off.** "If should-not-trigger queries are false-triggering, the description may be too broad… **clarify the boundary between this skill and adjacent capabilities**"; Claude Code's troubleshooting entry for "Skill triggers too often" is "make the description more specific." Since wording length is reach, a routing line cannot be narrowed out of an overlap without breaching ADR 0013's floor.
- **But the vendor's other remedy is additive, and ADR 0014 does not reach it.** The first-party fix for a skill that over-triggers against a specific neighbour is a **negative trigger naming that neighbour**: `Use for statistical modeling, regression, clustering. **Do NOT use for simple data exploration (use data-viz skill instead)**` ([Complete Guide to Building Skills](https://resources.anthropic.com/hubfs/The-Complete-Guide-to-Building-Skill-for-Claude.pdf)). That clause *adds* words while *subtracting* reach — a case ADR 0014's "wording length and reach are the same quantity" does not cover, and a candidate answer to #116's "explicit disambiguator" that does not breach the floor. It is offered here as a lead for #116, not as a finding: its effect is measured per description, never specified, and it requires one position's line to name another, which is a cross-line dependency the per-line check cannot see.
- Anthropic names the competition without resolving it, and its own tooling says so: "**The description competes with other skills for Claude's attention** — make it distinctive," and eval sets should include "cases where this skill competes with another **but should win**" ([`skill-creator`](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)). The remedy on offer is always *word it better and measure the hit rate*. The underlying principle is stated once, and it is the strongest sentence in the corpus: "**If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better**" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

## Q4 — Does the answer vary by reading agent?

**Verdict: yes, at three layers, all stated first-party rather than inferred. This is the finding that decides #116 item 4.**

- **By model.** "**Skills act as additions to models, so effectiveness depends on the underlying model.** Test your Skill with all the models you plan to use it with… **What works perfectly for Opus might need more detail for Haiku**" ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). Ambiguity is the regime named as degrading first: behaviour "is not guaranteed, especially for **more ambiguous prompts and for less capable models**." Two adjacent routing lines *are* the ambiguous case.
- **By harness.** Catalog in the system prompt or in a tool description — "Both work." File-read activation or a dedicated tool. Frontmatter stripped or not. Even name-collision resolution differs by surface within one vendor: Claude Code shadows the loser, while Managed Agents keeps both — "**both are available; each is announced with its own path**" ([Managed Agents — Skills](https://platform.claude.com/docs/en/managed-agents/skills)). Subagents have a five-level precedence table for shared names and an admitted undocumented case for same-directory duplicates, "**chosen by filesystem read order rather than a documented precedence**" ([Subagents](https://code.claude.com/docs/en/sub-agents)).
- **By run.** Nondeterministic by the vendor's own word, which is why the vendor's test reports a rate.
- The [client showcase](https://agentskills.io/clients) lists dozens of independent implementations — Claude Code, Codex, Cursor, Gemini CLI, Copilot, Goose, Letta and more — each making those choices for itself, under a spec that is a file-format and discovery contract and says so.

## Bottom line

**Neither specified nor observed — *measurable*, per description, per model, per harness. That is the answer, and it is the answer #118 was opened to get.** No first-party source specifies what happens when two natural-language discovery lines both match. The implementer's guide tells clients not to build the layer that would specify it and hands activation to "the model's own judgment"; MCP puts selection outside the protocol; the vendor's own remedy for ambiguity is to engineer it away upstream — consolidate, namespace, cap the candidate set — which is an admission that nobody has specified what happens when it is not engineered away. An unspecified, nondeterministic, harness-dependent behaviour cannot be designed against.

**On the substance, ADR 0013 was right and the retraction over-corrected.** The nearest first-party statement of this exact case — two always-loaded natural-language lines, both applying — is Claude Code's memory doc: "all discovered files are concatenated into context rather than overriding each other," and "if two rules contradict each other, Claude may pick one arbitrarily." Skills corroborate: multiple skills load for a single task, and the named cost is *conflicting instructions*. **One-wins is documented nowhere, on any surface, by any vendor.** The prototype's contrary line has no standing — a pre-publication authoring rationale on a constructed accrual, not a retrieval anyone ran. ADR 0013's claim can be restored as the better-supported reading, but only as a reading: the mechanism offers no guarantee, so the honest posture is that a reader **may** get both, may get one, and the record cannot make it either.

**Where this leaves #116.** Item 1 is **out of scope as a design question** and should be recorded as a fact about the reading agent. Item 4's own hypothesis is confirmed on first-party evidence. That does not dispose of the ticket: item 2 — what becomes of a **superseded** position's routing line — is a decision this design owns regardless, because it is about what the record *contains*, and containment is the one lever every source agrees the artifact controls. Item 3 likewise survives, being a question about the position files rather than the matcher. The narrow half is out of scope; the sharper half is not, and it is the half that is actually decidable.

**Two flagged consequences that belong to the map rather than to #116.** First, and larger than this ticket: **a perfect lexical match does not guarantee consultation.** Agents "typically only consult skills for tasks that require knowledge or capabilities beyond what they can handle alone," and a request may not trigger a skill "even if the description matches perfectly," because the agent judges it can handle the task itself. The stance index's whole premise is that a downstream agent hitting a dilemma will consult it; the operative predicate is not lexical match but perceived need, and a confident agent is exactly the reader most likely to skip the record. Second: **the always-loaded tier can be silently truncated by the harness on a key the record does not control.** Claude Code "shortens descriptions to fit the listing's character budget, which can strip the keywords Claude needs to match your request," and "when the listing overflows, **drops descriptions starting with the skills you invoke least**" ([Skills](https://code.claude.com/docs/en/skills)). A frequency-ordered drop is a real ranking layer — over *presence*, not over match — and it would delete the least-consulted routing lines first, which on a stance record are the rarest and therefore most valuable positions. That bears directly on the 25KB tripwire and on [#112](https://github.com/98kb/skills/issues/112)'s question of what sheds.

**What was searched and found empty.** Agent Skills specification, implementer's guide, description-optimization and best-practices guides, four Anthropic skills pages, Claude Code skills/subagents/memory, `skill-creator` source, MCP spec 2025-06-18 and 2026-07-28, MCP client best practices, Anthropic tool-use pages and two engineering posts, OpenAI and Gemini function-calling guides: no selection algorithm, no ranking over descriptions, no tie-break on match, no catalog ordering semantics, no cap on how many lines may match, no statement that one match excludes another. Published numbers exist but are all about **cardinality** — accuracy degrades past 30–50 tools, keep under 20 functions — and none about **similarity**; nothing quantifies what two close descriptions do, and the prototype's collision bites at two entries, far outside any measured regime.
